### 3. 定时任务多副本复核（结论：5 个全部数据幂等，修了 2 个真问题）

逐个核对 `AutoDataTask`、`OrderAutoReceiptReconcileTask`、`PayOrderTask`、
`ImageModerationCleanupTask`、`UserTempBanReconcileTask` 的 CAS 条件与外部副作用：

- `AutoDataTask`（真问题）：`@PostConstruct` 让每个副本启动都跑一次日结；而
  `INSERT ... ON DUPLICATE KEY UPDATE` 在"值未变"时返回 0 行，原代码把 0 行当失败抛异常回滚
  → 多副本/重启必然误报。已改为启动补齐事件 + 与定时共用分布式锁，并把 0 行视为"值未变"。
- `PayOrderTask`（真问题）：每 5s 无锁轮询支付渠道，多副本会让外部调用量翻 N 倍。已按现有
  `setIfAbsent` 范式加锁（键带 `applicationName`）。
- 其余三个（回执对账/图片清理/临时封禁对账）：靠条件 UPDATE 保证幂等，**不加锁也不会重复落账**，
  仅记录依据不改动。

### 4. 订单创建的真 bug（压测中被暴露）

`OrderItemMapper.xml` 的 `insertBatch` / `insertOrUpdateBatch` 列清单与 VALUES 元组各有一个
**硬编码尾逗号**，生成的 SQL 恒为 `... refund_order_id, )values (... #{item.refundOrderId}, )`——
语法错误。实测 `order_info` 长期 0 行，即**下单功能从未成功过**；单元测试全部 mock 掉 mapper，
所以 CI 全绿也发现不了。已修复（4 处），并在三节点滚动重建。

### 5. 上传共享化

node1 导出 `/opt/smartlect/run/uploads`（NFS，仅放行 node2/3 两个 IP，`no_root_squash` 因服务以 root 运行），
node2/3 挂载同路径（`hard,timeo=100,_netdev,nofail`）。数据本就在 node1，无需迁移。

### 6. nginx 网关多后端

`/api/` 从写死 `127.0.0.1:18080` 改为 `upstream smartlect_gateway`（三节点内网，
`max_fails=3 fail_timeout=10s` + `keepalive 64`）。可逆：apply 前备份，revert 还原。

## 性能测试

### 测具与关键纠正

自研的 Python(asyncio) 发压器在 **400 并发 TLS 长连接下把 4 核发压机打满 100%**，
用它测出的"277 req/s 墙"其实是发压机的极限。改用 k6（Go）后同一台机器可推到
2000+ req/s，才探到被测系统的真实天花板——**这一条如果没发现，整份结论都是错的**。

最终测具：**k6 v0.54.0**（发压机 node4，走内网 https 到 node1 的 nginx，与真实用户路径一致）。
限流口径分两组：生产配置（200 QPS/实例）与解除限流（2000/实例）；**极限值取解除限流组**，
否则测到的是限流器的配置值而非系统算力。

### 极限值与拐点

拐点口径（写死在 `analyze-knee.py`，可复算）：
低负载基线 p95 = 最小并发档的 p95；延迟拐点 = p95 首次 ≥ 2× 基线的最小并发；
吞吐拐点 = 吞吐相对上一档增幅 < 10% 的并发。

**形态 A：单机（应用只在 node1）——解除限流**

| 并发 | req/s | p50 | p95 | p99 | 错误率 |
|---|---|---|---|---|---|
| 200 | 284.43 | 4.7ms | 18.0ms | 111.8ms | 0% |
| 400 | 560.02 | 4.9ms | 34.2ms | 539.1ms | 0% |
| **600** | **803.66** | 5.9ms | 234.9ms | 1040.3ms | 0% |
| 800 | 721.18 | 191.7ms | 1328.0ms | 1850.8ms | 0% |
| 1000 | 719.59 | 591.5ms | 1820.1ms | 2520.5ms | 0% |
| 1200 | 732.92 | 969.5ms | 2206.1ms | 2909.6ms | 0% |
| 1600 | 722.75 | 1707.7ms | 3361.7ms | 4241.7ms | 0% |

- **峰值 = 803.66 req/s @ 600 并发**（p50 5.9ms、p95 235ms、零错误）
- **延迟拐点 = 600 并发 / 803 req/s**；**吞吐拐点 = 800 并发**

**两形态对比（解除限流）**

| | 形态 A 单机 | 形态 B 集群 | 差异 |
|---|---|---|---|
| **峰值吞吐** | **803.66 req/s** @ 600 并发 | **832.32 req/s** @ 1600 并发 | **+3.6%** |
| 延迟拐点 | 600 并发 / 803.66 req/s | 600 并发 / 811.09 req/s | +0.9% |
| 拐点处 p95 | 234.9ms | 200.6ms | −15% |
| 低负载 p95（200 并发） | **18.0ms** | 38.5ms | **2.1× 更差** |
| 过峰行为 | 吞吐回落到 722 | 吞吐稳在 774-832 | 集群更耐过载 |

**结论（诚实的版本）**：三节点集群的峰值只比单机高 **3.6%**，而且低负载下延迟反而翻倍——
因为 node2/node3 是 2 核机器且要同时承载 RabbitMQ/Nacos/Redis，实测 **load average 7.2（2 核）**，
早已 CPU 饱和；1/3 的请求被轮询到这两个慢节点，把尾延迟拉高、把整体吞吐压住。
集群带来的真实价值在**过载行为**（吞吐不回落、零错误）与**可用性**，而不是吞吐倍数。

## 踩坑实录（按踩到的顺序）

1. **VPC 网段与 Docker 默认网桥重叠**（最隐蔽的一条）：阿里云 VPC 是 `172.16.0.0/12`，
   Docker 默认网桥 `docker0` 是 `172.17.0.0/16`，两者重叠。发压机的内网 IP `172.17.40.108`
   正好落在这个区间，于是 node1/2/3 的**回包全被丢进 linkdown 的 docker0**，报文体现在
   "双向内网完全不通、连 ICMP 都不通"，极易误判为安全组。修复：给发压机地址补一条
   `/32` 主机路由（比 `/16` 更具体，优先生效），并做成 systemd 单元持久化
   （`deploy/cluster/scripts/fix-vpc-route.sh`）。长期建议见"未完成项"。
2. **只停不删的残留容器会挡名字**：node2/3 上 9 月的孤儿容器我先用 `docker stop` 停了释放端口，
   但没删容器——新集群的 `rabbit-c2/c3` 起来时撞名失败。停机窗口里被迫中断处理。
3. **门禁脚本在最后一行崩**：`apps_check` 的汇总打印把 `app_services()` 返回的元组当集合做
   `&` 运算，`TypeError`。12 个进程其实全部健康，是脚本自己失败导致 `systemctl start` 报错。
   已把该计算抽成 `java_service_count()` 并加进自检断言。
4. **nginx upstream 被写成列表字面量**：`path, port, *ips = sys.argv[1], sys.argv[2], sys.argv[3:]`
   ——`*ips` 拿到的是嵌套列表，格式化进配置后成了
   `server ['172.21.131.151', ...]:18080`。且**失败发生在写文件之后、reload 之前**，
   配置已坏但 nginx 仍在用内存里的旧配置跑（站点未受影响）。已修正解包并加 `nginx -t` 前置。
5. **`set -u` 下 `local a=$1 b=$a` 报未绑定**：把 `local` 拆成多行即可。
6. **发压机才是瓶颈**（方法论级）：自研 Python 发压器在 400 并发 TLS 长连接下 4 核打满 100%，
   测出的"277 req/s 墙"是发压机极限。换 k6（Go）后同一台机器可推到 2000+ req/s。
   这一条如果没发现，整份性能结论都是错的。
7. **冷 JVM 污染首档**：形态切换后立刻开跑，node2/node3 的 JIT 未编译，首档 p95 2.5s 与相邻档
   43.7ms 严重背离。已改为切换后预热再跑，并作废那批数据。
8. **变量名撞车**：套件里 `LAUNCHER` 已是发压机 IP，我拿它当发压器选择器用，静默失效
   （跑了 Python 却以为是 k6）。改用 `LOAD_ENGINE`。
9. **内部接口的身份头**：除 `X-Internal-Token` 外，`/internal/**` 还要求
   `X-Smartlect-User-Id`（委托身份，刻意走请求头而非 body——body 可被提示注入改写）。
   9 月的脚本没这个头，直接 401。
10. **SQL 细节两处**：`sku_stock` 主键是 (product_id, property_value_id_hash) 而非自增 id；
    32 位十六进制哈希不加引号会被 MySQL 当标识符，报 `Unknown column '<hash>'`。
    另：跑 SQL 时反复被"SSH + docker exec + mysql -e"三层嵌套引号坑，最后统一改成
    "写脚本文件上传执行"。
