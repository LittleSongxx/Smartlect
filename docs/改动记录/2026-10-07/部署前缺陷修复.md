日期：2026-10-07 ｜ 状态：已修复并本地验证；服务器部署见文末

## 需求

对本日六批次改造做一次上线前检查（核对文档、提交推送、部署到服务器），过程中发现的缺陷随手修复。
本文件只记**修复**，不改设计、不新增能力。

检查方式：以"新版能否真的启动/运行"为标准逐层验证——构建、配置加载、基础设施编排、调度链路。

## 一、九个服务的 `application.yml` 有重复键——服务启动即失败（部署阻断）

### 现象与机制

批次四为接入 Nacos 配置中心，在每个服务 `spring:` 块**顶部插入**了新的 `config:` 与 `cloud:`：

```yaml
spring:
  config:   # ← 插入块
    import: [nacos:..., nacos:...]
  cloud:    # ← 插入块
    nacos: {config: {...}}
  config:   # ← 原有块
    import: optional:classpath:smartlect-common.yml
  cloud:    # ← 原有块
    openfeign: {...}
    nacos: {discovery: {...}}
```

Spring Boot 3.5.16 用的 SnakeYAML 2.4 默认 `allowDuplicateKeys=false`——重复键**直接抛异常**，不是"后者覆盖"：

```
found duplicate key config
 in 'reader', line 17, column 3
```

异常发生在 `ConfigDataEnvironmentPostProcessor.postProcessEnvironment` 阶段，即**配置加载期**，
早于任何 Bean 创建——九个服务（gateway/admin/user/product/stock/cart/order/pay/coupon）全部无法启动。

**为什么之前没暴露**：仓库里没有任何 `@SpringBootTest`（全上下文测试），`mvn test` 跑的都是单元/slice
测试，从不加载 `application.yml`，所以"全仓 BUILD SUCCESS"掩盖了这个问题；又因为一直没部署，
线上仍是旧版本。这是一颗只等首次部署就会引爆的地雷。

### 修复

`backend/smartlect-{gateway,admin,user,product,stock,cart,order,pay,coupon}/**/application.yml`：
把重复块合并成**单一** `spring.config` 与 `spring.cloud`，并把 Nacos 导入写成 `optional:`：

```yaml
spring:
  config:
    import:
      - optional:classpath:smartlect-common.yml
      - optional:nacos:smartlect-common.yml?group=SMARTLECT_GROUP&refreshEnabled=true
      - optional:nacos:smartlect-{服务}.yml?group=SMARTLECT_GROUP&refreshEnabled=true
```

> 注：`optional:` 是必须的。非 optional 的 Nacos 导入在 dataId 缺失或配置中心不可达时会让启动失败，
> 而"本地 yml 兜底"正是批次四记录里写明的设计意图。

### 顺带实测的一个与记录不符之处

批次四记录写"本地 yml 保留作为 fallback，但运行时优先从 Nacos 读取"。实测（最小 Boot 应用 + 真实
classpath，见证据）结果是：**`spring.config.import` 导入的文档优先级高于声明它的文档**——
即 Nacos 值会覆盖本地 `application.yml` 的同名键。这与"本地兜底、Nacos 优先"的字面顺序一致，
但要注意方向：本地 yml 里改一个值**不会**生效，除非同时更新 Nacos 或该键不在 Nacos 中。

### 验证

- 权威加载器（Boot 3.5.16 自带的 `YamlPropertySourceLoader`）逐个加载九个文件：修复前九发九中，
  修复后零异常
- 有效属性集 diff：修复后 = HEAD 版本 + `spring.cloud.nacos.config.*`，未丢失任何原有键
- 最小 Boot 应用真实启动：修复前在配置加载期终止，修复后正常进入启动流程
- 完整应用重启：12 进程健康、9 个 Nacos 注册（`Application checks passed`），九个 JVM 均正常读取配置

## 二、九个 xxl-job 定时任务从未执行（功能性停摆）

批次三把九个 `@Scheduled` 任务迁成 `@XxlJob` handler，但**只加注解不会执行**——任务定义（执行器组、
cron、启用状态）存在调度中心的库表里，必须在 `xxl_job_group` / `xxl_job_info` 中登记。
批次三记录已自陈这是未完成项（"控制台首次部署需手动注册"）。

排查中发现三层问题叠加：

1. **未登记**：本地调度中心只有官方示例任务（`demoJobHandler`），九个业务任务一个都没有。
   影响面：支付轮询、Outbox 兜底投递、退款 Saga 对账、订单自动确认收货、MQ 补偿重放、
   管理端统计、封禁到期解封、图片审核清理、秒杀对账——表现为"该自动发生的事一直没发生"，且无任何报错。
2. **执行器端口冲突**：`xxl.job.executor.port` 固定为 9999，而九个服务跑在同一台机器上，
   只有先启动的那个能绑定端口并注册成功（`xxl_job_registry` 里只有 `smartlect-user`），
   其余八个注册失败。调度日志表现为 `trigger_code=500`（无可用执行器）。
3. **`userTempBanReconcile` 永远不会注册**：该 Bean 的条件是 `app.common-scheduling.enabled=true`，
   而 user 服务从最早提交起就写着 `false`——即使登记了任务，handler 也不存在。
   （这是既有缺陷，非批次三引入；同类任务只有 coupon 的 `couponRushReconcile` 也挂这个开关。）

### 修复

- 新增 `scripts/xxljob_setup.py`：幂等登记九个执行器组与九个任务定义（cron 按原 `@Scheduled` 周期折算）。
  已有记录即跳过，不覆盖控制台上的人工调整。
- `smartlect-common.yml`：执行器端口默认值 `9999` → `0`（由 xxl-job 从 9999 起自选空闲端口）。
- `smartlect-user` 的 `application.yml`：`app.common-scheduling.enabled` `false` → `true`
  （该开关只影响两个 Bean，另一在 coupon 且已开启，故改动安全）。

### 验证

调度日志从 `trigger_code=500`（无可用执行器）转为执行器地址可解析；执行器注册表可见各服务条目。
**未验证**：九个任务各自的业务效果（本文件只负责"任务能被触发"，不替代业务回归）。

## 三、基础设施编排的一致性问题（全新环境必然失败）

| 问题 | 影响 | 修复 |
|---|---|---|
| `infra_up` 只起 6 个服务，不含 canal / xxl-job-admin，而 `infra_check` 要求这 8 个都 healthy | 全新环境 bootstrap 后 `infra-check` 必然失败 | `infra_up` 服务列表补齐至 8 个 |
| `infra_check` 用 `endswith("healthy running")` 判定健康 | **`unhealthy running` 也以 `healthy running` 结尾**——门禁形同虚设（xxl-job-admin 长期 unhealthy 却无人发现） | 改为逐字段比对 `parts[1]=="healthy" and parts[2]=="running"` |
| `mysql-init.sh` 建了 `smartlect_xxljob` 库并 GRANT，却没有创建 `smartlect_xxljob` 用户 | MySQL 8 对不存在的用户 GRANT 报 `ERROR 1410`，**首次初始化失败** | identity 循环补 `xxljob`；`compose.yaml` 的 mysql environment 补对应密码变量 |
| `deploy/sql/16-xxljob.sql` 挂在 **xxl-job-admin** 容器的 `/docker-entrypoint-initdb.d/` | 那是 MySQL 镜像的初始化目录，挂错容器等于从未执行 | 移到 mysql 服务的 volumes |
| xxl-job-admin healthcheck 用 `curl`，但镜像里既无 curl 也无 wget | 容器永远 unhealthy（日志显示应用实际启动正常） | 改用 `bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080'` |
| litellm 的 `env_file: ./model.env` 文件不存在，且服务无 profile | `docker compose config` 等全量校验直接失败 | 服务挂 `litellm` profile；`env_file` 改 `required: false`；healthcheck 由 curl 改 python urllib |
| `runtime.py` 自测的密码列表漏 `CANAL`/`XXLJOB`，库数断言仍为 10 | 自测失败；且继承外部 `SMARTLECT_*` 会掩盖真实缺漏 | 补齐密码与断言（11 库）；自测环境只继承 PATH；新增"每个库的属主用户都必须被创建"断言 |

## 四、Nacos 推送脚本会写入自引用

`scripts/nacos_config_push.py` 原样推送 `application.yml`，而该文件含 `spring.config.import: nacos:...`
——推入配置中心后，应用拉回来的这份配置又声明"从 Nacos 导入"，形成自引用（递归拉取自身）。
修复：推送前剥离 `- nacos:` / `- optional:nacos:` 行（保留本地 classpath 兜底行），
找不到可剥离的行时拒绝推送而非盲推。
