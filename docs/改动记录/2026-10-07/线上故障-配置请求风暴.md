# 线上故障：配置请求风暴写满磁盘，MySQL 退出致站点只剩静态页

日期：2026-10-07 ｜ 状态：已恢复并根治（线上验证通过）

## 现象

站点打不开业务功能，**只剩 nginx 服务的静态页面**；网关 `/actuator/health` 返回 503。

## 排查过程（按发现顺序）

1. **容器少了两个**：`smartlect-mysql-1` 不见了（`Exited (2)` 5 小时前），`smartlect-xxl-job-admin-1` 也曾被 OOM 杀（`Exited (137)`）。应用进程都还在（`smartlect-apps` active），但连不上数据库。
2. **磁盘 100% 满**：`/` 40G 用尽、0 可用。MySQL 因无法写入而退出——这是站点不可用的直接原因。
3. **磁盘被日志吃满**，占用来源：

| 文件 | 大小 |
|---|---|
| Nacos 服务端 `core-auth.log` + 轮转 | 2.5 G |
| Nacos 服务端 `config-client-request.log` | 954 M |
| Nacos 服务端 `config-trace.log` / `config-pull-check.log` / `naming-distro.log` | 494 M / 363 M / 103 M |
| `run/logs/smartlect-product.log.1`（已轮转） | 3.3 G |
| 其余 8 个服务当前日志 | 各约 160 M |

4. **定位到配置请求风暴**：
   - Nacos 服务端 `config-client-request.log` 显示客户端每 200ms 发一次 `listen` + `get`，**`rt: 1ms`**——长轮询没有挂起，退化成了高频短轮询
   - 应用侧日志每 200ms 一条 `[data-received]`，而 **md5 完全未变**（`26b1781d…`），说明配置根本没有变化
   - 120 秒窗口实测：9 个服务合计 **8193 条** `data-received`

## 根因

**Nacos 客户端 3.0.3（随 Spring Cloud Alibaba 2025.0.0.0 引入）与线上服务端 2.5.3 集群的组合下，配置长轮询未生效**。

- 服务端三节点 readiness 全部 OK，集群自身健康（`naming-distro.log` 是正常同步记录）
- 本地单机环境同样复现（`user.log` 涨到 285MB）
- 官方文档把 3.x 客户端列为兼容 2.5 服务端，未记录该症状，属边界缺陷

**为什么这次才暴露**：配置中心是批次四的改动，但当时九个服务的 `application.yml` 有重复键（SnakeYAML 2.4 直接报错），配置中心从未真正跑起来；本日修掉重复键后首次上线，问题随之出现。

## 处置

### 一、恢复（先让线上可用）

1. 清理日志：应用轮转文件删除 + 当前文件就地截断，Nacos 容器内 4.9G 日志截断 → 释放约 10G
2. `docker start smartlect-mysql-1`（数据卷未受损，container 正常起来并 healthy）
3. 启动 `smartlect-xxl-job-admin-1`，重启应用
4. 结果：站点 200 / 网关 200 / 用户端 200 / `/api/product/loadProduct` 200，6 个容器全 healthy

### 二、止血（防止再次写满）

新增 `/opt/smartlect/scripts/log_guard.sh`，由 `/etc/cron.d/smartlect-log-guard` 每 5 分钟执行：

- 任何应用日志单文件超过 50MB 就地 `truncate`（保留文件句柄）
- 删除已轮转的 `*.log.*`
- 根分区占用超过 70% 时，同时收敛 Nacos 容器内的日志

### 三、根治（方案 A：关闭变更监听）

九个服务的 `spring.config.import` 由 `refreshEnabled=true` 改为 `false`：

```yaml
- optional:nacos:smartlect-common.yml?group=SMARTLECT_GROUP&refreshEnabled=false
- optional:nacos:smartlect-{服务}.yml?group=SMARTLECT_GROUP&refreshEnabled=false
```

配置仍在**启动时**从 Nacos 加载（配置中心能力保留），但不再注册变更监听，长轮询随之消失。
**仓库内没有任何 `@RefreshScope` Bean**（这一点本就记录在案），热刷新没有消费者，因此无功能损失。

选它的理由：改动最小、无功能损失、直接消除风暴源头。备选方案（客户端降级到 2.5.x / 服务端升到 3.x）都保留监听能力，但需要更大的改动与验证。

## 验证

**本地先行**（避免无效部署）：同一台机、同一时段 90 秒口径——

| 指标 | 修复前（`refreshEnabled=true`） | 修复后（`false`） |
|---|---|---|
| `data-received` | 8193 条 | **0 条** |
| 应用日志 | 2.7 MB | 20 KB |

**线上部署后**（120 秒窗口，清空日志后计时）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 9 服务合计 `data-received` | 8193（90 秒口径） | **0** |
| Nacos 端日志 | 秒级 MB | 44 KB |
| 磁盘 | 0 可用（100%） | 7.6 G 可用 |

`apps-check` 通过（12 进程健康 + 9 个 Nacos 注册），站点 301、网关 200 正常。

## 遗留与后续

- **日志闸门保留**作为纵深防御（即使将来出现别的日志风暴也不会写满磁盘）。它是治标手段，会周期性清空日志，排障时需注意日志可能不完整。
- **未做**：不在本次范围内验证"Nacos 配置变更后是否需要重启应用才能生效"的运维口径——答案是**需要重启**（监听已关闭），这一点应补进 `docs/runtime.md` 的配置中心说明。
- **未做**：xxl-job-admin 曾被 OOM 杀（`Exited 137`），未深挖其内存峰值；它 `mem_limit: 512m`，若再次发生可考虑上调或加 `restart: unless-stopped`。
- 服务器上 `/opt/smartlect` 的 `git stash` 内仍留有更早的工作树改动（内容均已被提交覆盖），可按需清理。
