## 一、索引层根治（4 项，已上线）

上午是用脚本补建的索引、靠 aiohttp 补装恢复的功能；这次把根因从代码上修掉：

| 问题 | 修复 |
|---|---|
| ES 写入嵌在「遍历向量」的循环里 → 无 embedding 的部署永远索引不到知识 | `knowledge._mirror_vector` → `_mirror_index`：按 `chunks_meta` **全量**写 ES，有向量时才写 Qdrant |
| BM25-only 发布只记任务、不写索引 | `indexing.record_sync_publish` 改为**真的写 ES**；新增 `index_bm25_only(scope, doc_id, version)` —— 也是存量环境重建索引的入口（发布接口对已 PUBLISHED 文档直接返回，此前没有任何路径能把它们补进检索层） |
| 默认分析器写死 `smartcn`，线上 ES 无该插件 → 建索引 400 | 改为**探测式**：`smartcn → cjk → 内置 standard`，逐个 `_analyze` 试探 |
| 建索引失败只记 WARNING，检索整层失效无人知 | 升为 **ERROR** 并写明后果（"ES/Qdrant 索引将不可用"） |

按"索引失败不阻塞发布"的既有口径，`index_bm25_only` 在无切片时返回 0 而非抛错（一处测试因此修正了断言预期）。

**验证**：336 项单测全绿；线上重启后启动日志中检索后端报错**从多处栈归零**。

## 二、复合关键词兜底拆词（已上线）

端到端测试发现：问"小猪B-BO 公仔有哪些规格？"答"未找到该商品"，而商品就在售。

直接调 Java 的 `searchOnSale` 复现，定位到文本谓词是**短语包含**（等价 LIKE）：

| keyword | 命中 |
|---|---|
| `小猪B-BO` | 1 |
| `小猪` / `MINISO` / `名创优品` | 各 1 |
| **`小猪B-BO公仔`** | **0** |

商品名里"小猪B-BO"与"公仔"之间隔着"弹力超柔趴姿"等字，整体短语不连续。

**修复**放在 `retrieval_variants`（该处的变体本就逐个检索并合并结果，天然是重试点）：
用 jieba 从 query 切出**最长实词**作为**最后一个**兜底变体——放最后，只有精确变体全空时才用到；
切不出两个词时返回空串，不制造噪声。变体上限 3 → 4。

自测：`小猪B-BO公仔 → 小猪`、`公仔`/`USB线` 不拆、`iPhone 17 Pro Max 手机壳 → iPhone`。

## 四、测试发现的两个未解决问题（模型侧）

### 1. 商品咨询仍答"未找到"——Java 检索已能命中，疑在模型侧

拆词修复已确认在线上生效（`_longest_keyword_term('小猪B-BO公仔') → '小猪'`），
Java 接口对拆出的词也都能命中（`小猪` 1 条、`iPhone` 1 条、`索尼` 2 条、`1000XM6` 1 条），
但模型回答依旧是"当前本店可售商品中未找到…"。

也就是说**问题不在检索层**，而在模型这一侧，两个可能方向：

- 模型自带了类目过滤（"有哪些规格"可能被映射成带 `categoryId` 的查询，而类目内叠加关键词会清零——代码里已有"类目内关键词放宽"分支，但只在**同时**给出 keyword 与 categoryId 时触发）
- 意图判定把商品咨询当成政策类问题（回答里那句"当前按全店政策回答"是其线索）

**下一步**：需要开 assistant 的检索可观测性（把命中的变体、召回条数、空结果原因打到日志），
才能区分是"没调到检索"还是"检索被过滤清空"。当前日志级别看不到这些。

### 2. 对比类问题触发预算超限

```
smartlect.agents.shopping.contract.BudgetExceeded: model_call_or_time_limit
```

对比多件商品会派发子智能体（1–3 个），每个都调模型，总调用数/耗时撞上预算上限后整轮失败，
用户看到"本轮模型通道未能完成回答…已转人工"。

有界预算是设计（防止单轮无限调用），但对比类是正常用法，不该整轮失败。**候选修法**：
给对比场景单独放宽调用预算、或子智能体之间串行化以压低并发时的瞬时额度消耗、或在超限时降级为
"逐个查证后给部分对比"而不是整轮转人工。需要先确认线上模型的实际响应时延，再定阈值。

## 第二轮：继续修（同日追加）

用户要求"再全部修一下"。第二轮在上述基础上又做了四项，并逐个上线验证。

### 5. 对比类问题：预算放宽（6 → 8）

`session.py:258` 的 `context['model_calls'] >= MODEL_CALL_LIMIT` 抛出
`BudgetExceeded('model_call_or_time_limit')`。对比类会派发 1–3 个子智能体，而子智能体的
模型调用按设计**计入同一预算**（dispatch 注释里的"预算单一事实源"），3×2 次子调用加主循环
几轮就把 6 撞满。

**两次调整才算对**：先放到 12，实测**从"预算不足"变成"超时"**——`TURN_DEADLINE_SECONDS=90`
是硬约束，模型单次调用约 8–12 秒，12 次必然拖过 deadline。最终取 **8**：比 6 多给对比留额度，
又在 90 秒内跑得完。

### 6. 新增"重建索引"接口（补上运维缺口）

`POST /admin-api/assistant/knowledgeIndex/rebuild`（需 merchant + `admin:legacy`，可带 `doc_id`）→
`IndexingService.rebuild_bm25()` 遍历已发布文档重写 ES。管理端此前只有"刷新文档列表"和
"重试失败任务"，而发布接口对已 PUBLISHED 的文档直接返回——存量数据没有路径补进检索层。

### 7. 检索可观测性

在 `shopping_retrieve.search` 记录 query / required_terms / excluded_terms / category_id /
变体列表 / 每个变体的命中数。**踩了个坑**：先用 `logging.getLogger("smartlect.retrieve")`，
线上日志里一行都没有——uvicorn 的 log config 之后创建的 logger 没有 handler，INFO 直接被丢；
换成 `uvicorn.error` 仍不可见。诊断期最终改为 `print(..., flush=True)`。

### 8. 提示词：商品断言必须来自本轮检索

检索轨迹证实：问"对比 iPhone 17 Pro Max 和索尼 WH-1000XM6"时**根本没有发生检索**，
模型凭上下文直接答"本店暂未上架"——而两款商品都在售（单问哪一个都能查到规格与价格）。
原提示词只写了"Java 事实决定价格、库存和交易状态"，没要求"商品是否存在也要先查"。

补上一句："商品是否存在、规格与价格同样只能来自本轮检索（search/recommend）结果：
用户点名了商品就先检索再回答，未检索到不得断言'未上架''无此商品'，而应说明本轮未检索到
并给出可选的下一步"。

**效果**：对比问题的措辞从"本店暂未上架"变成了"**经检索**，当前店铺中未找到…"——
模型确实去查了。**这条改动影响所有回答，需按仓库惯例复跑 quality-v2 评测确认没有回退。**
