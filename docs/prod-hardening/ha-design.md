# T2-9 HA 架构设计 + 故障演练记录

日期：2026-09-14 ｜ 状态：**已完成**（文档 + 4 组件实测演练） ｜ 结论先行：当前是「单机容器编排」架构，**容器级故障可自愈（实测 10-43 秒），主机级故障 RTO≈3 分钟（重启实测）、RPO=最近日备**；升级到真高可用的月成本量级约 ¥1000-1500，对演示/求职场景不划算，风险以「清单+监控+演练」管理。

## 1. 当前架构与已知风险清单（诚实版）

单 ECS（4c16g，按量）承载全部：5 中间件容器（compose）+ 13 应用进程（runtime.py）+ 监控栈。风险按严重度：

| 风险 | 影响 | 现有缓解 |
|---|---|---|
| **ECS 宿主机/系统盘故障** | 全站不可用 | ESSD 云盘后端多副本（物理坏盘云平台兜底）；PITR 备份可异地重建（RTO≈30 分钟级重建栈，RPO=日备+binlog 副本） |
| **单 AZ** | 机房级故障全灭 | 无（需多 AZ 部署，见升级路径） |
| MySQL 容器故障 | 写入中断（浏览部分缓存兜底） | 容器自愈 12s；PITR |
| RabbitMQ 单节点 quorum | **队列不可用即无多数派**——quorum 队列在单节点上没有重选举可言，broker 宕=消费停（worker 受控重试） | 容器自愈 10s |
| Nacos 单点 | **新调用**的发现受影响（LB 有实例缓存，实测 90s 宕机流量无感） | 容器自愈 43s，客户端自动重注册 |
| Seata 单点 | 分布式事务全部失败（下单 500） | 容器自愈 16s；fail-fast 无半提交 |
| 备份与数据同盘 | 盘损同灭，RPO 退化到日备年龄 | 已量化（T0-2）；OSS 异地为可选增强 |
| CI 部署依赖 22 端口 | SG 若收紧源 IP 会断部署链 | 待 T1-8 一并处理（放行 GitHub runner IP 段） |

## 2. 故障演练实录（2026-09-14 23:36-23:47，每项均为真实 docker kill）

| 组件 | 宕机时长 | 用户可见影响 | 技术表现 | 恢复耗时 | 数据一致性 |
|---|---|---|---|---|---|
| MySQL | 106s | 浏览接口状态码仍 200（缓存兜底）；未缓存路径 CommunicationsException | 连接池报 Connection refused | **12s**（docker start 至 healthy） | 对账 184780=184780 全平 |
| Nacos | 90s | **零感知**（3×loadCategory + session 全 200） | LB 实例缓存兜底；恢复后 9 服务自动重注册 | **43s** | 全平 |
| Seata | 25s+ | 浏览无感；**下单 1.6s 快速失败（HTTP 500，无半提交）** | TM 无法开全局事务，fail-fast | **16s** | 全平（8 undo 表正常） |
| RabbitMQ | 60s | 浏览/会话无感 | worker 日志：`Commerce consumer retry after AMQPConnectionError` 受控重试；**单节点 quorum 无重选举可观察（无多数派即不可用）** | **10s** | 全平 |

演练方式：kill 前先跑全量备份；`docker kill` → 观测（curl 探测 + 日志样例 + Alertmanager）→ `docker start` → 等健康 → `apps-check`（13/9/8）→ `recon.sh` 对账。

## 3. 演练直接产出的监控修复

- **新增告警 `SmartlectMySQLDown`（mysql_up==0 持续 1m，critical）**：演练暴露 MySQL 容器宕机时 mysqld-exporter 自身仍响应（scrape `up`=1），原规则整库不可用也不报警——这是全链路里最值钱的一个发现。
- 已验证 rabbitmq 不可用会触发 `SmartlectServiceDown`（T0-1 pause 演练）；本次 kill 观测窗 60s 未及 `for:1m` 窗口，属时序而非盲区。
- 遗留小盲区（已记录不修）：Nacos 无独立 exporter（其宕机靠 LB 缓存兜底+注册数间接可见）。

## 4. 升级路径与成本对照（量级估算，以官网实时价为准）

| 目标 | 方案 | 月成本量级 | RTO/RPO 收益 |
|---|---|---|---|
| MySQL 高可用 | RDS 高可用版（半同步主备+自动切换）替代容器 | ¥300-800 | RTO<30s（自动），RPO≈0；免自运维备份（但保留 ossutil 异地思路） |
| Redis 高可用 | Tair/Redis 标准版双副本（或自建哨兵 2×小机） | ¥100-200 | 主从秒级切换 |
| RabbitMQ 高可用 | 3 节点 quorum（3×2c4g）或阿里云消息队列版 | ¥450-700 | 真正的 quorum 重选举，单节点故障无感 |
| Nacos 高可用 | MSE Nacos 开发/标准版，或 3 节点自建 | ¥200-600 | 注册中心无单点 |
| 应用多副本 | 2×ECS 应用双副本 + SLB | 增量 ¥500-800 + SLB ¥50-100 | 滚动发布零停机、单机应用故障无感 |
| **合计** | 全家桶 | **约 ¥1000-1500/月** | 从「单机自愈」到「组件级 HA」 |

**决策建议**：当前阶段（演示+作品集）单机+容器自愈+日备+监控告警是正确的性价比选择；若未来承接真实流量，按「RDS → 应用双副本+SLB → RabbitMQ 三节点」顺序升级（先把权威数据层高可用，再扩无状态层，最后是中间件集群）。

## 5. RTO/RPO 现状汇总（实测数字）

- 容器级故障：RTO 10-43s（自愈），RPO=0（durable 卷 + MySQL redo/binlog）
- 应用进程级：runtime.py 幂等 up，重启全栈约 3 分钟（含 9 Java 启动+注册）
- 主机级：重启实测约 3 分钟全栈恢复；**主机损毁：重建栈 ~30-60 分钟（脚本化），RPO=最近日备（最坏 24h，binlog 每日外带）**
- 演练破坏面控制：每次 kill 前 fresh 全量备份；四轮演练后对账零差异

## 面试一句话

对单机架构做了诚实的可用性工程：四个关键组件逐一真实 kill 演练，量化出容器级 10-43 秒自愈、Seata 宕机下单 1.6 秒快速失败无半提交、Nacos 宕机 LB 缓存零感知，并在演练中抓出并修复「MySQL 整库宕机不告警」的监控盲区；同时给出带月成本量级的分阶段 HA 升级路径与决策建议（先数据层后无状态层），而不是无脑堆机器。
