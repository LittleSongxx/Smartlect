## 关键口径

- **合并两台发压机时**：QPS 直接相加（精确）；百分位**不能相加**，所以表里给出两台各自的值
  与其中的最大值作保守上界。两台 p95 差 <1.5%，说明发压机不是瓶颈。
- **每档 60s**，跑前按固定协议预热；浏览场景三请求（首页/分类/商品列表），QPS 为 k6 请求口径。
- **发压机的容量是新引入的干扰**：单台 4 核在 1217 req/s 时自身 CPU 已 72%，
  所以必须上第二台——判别方法就是看发压机自己的 CPU，超过 70% 的数字不可信。

## 结论速览（node1, 8c16g）

| 口径 | 值 |
|---|---|
| 峰值吞吐 | **1227 req/s** @2400 总并发（CPU 98%，p95 2.3s） |
| 健康顶格 | ~1070 req/s @800 总并发（p95 255ms，CPU 91%） |
| 拐点 | 约 1100-1170 req/s |
| 约束 | node1 的 8 核 CPU |
| 提上来的杠杆 | JVM 处理器预算 2→4、堆 256m→512m（+47%）；连接池 8→16 无收益 |
